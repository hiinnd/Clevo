# CLEVO authentication/security changes

Subsequent integration phases (2026-11-16): [NOTIFICATIONS.md](NOTIFICATIONS.md), [TRACKING_ARCHITECTURE.md](TRACKING_ARCHITECTURE.md), and [NOTIFICATION_TEST_RESULTS.md](NOTIFICATION_TEST_RESULTS.md) describe migrations 007/008, current delivery/tracking policy and test evidence. The API now has 159 operations across 138 paths. Earlier phase counts and worker/null-transport behavior below are historical where superseded.

Phase date: 2026-11-15. This phase implements authentication and authorization hardening on the existing PHP/MySQL application. No backend framework replacement, mobile app, production deployment, provider-account rotation or real payment integration was performed. The [audit](AUDIT_REPORT.md) remains a historical record of the pre-change baseline.

API contract: [AUTHENTICATION_API.md](AUTHENTICATION_API.md). Executed validation and limitations: [SECURITY_TEST_RESULTS.md](SECURITY_TEST_RESULTS.md).

## Implemented changes

| Area | Implementation / files | Result |
|---|---|---|
| Environment and failure handling | `includes/security/environment.php`, `includes/config.php`, `.env.example` | Dotenv/process configuration; independent APP/JWT keys; production validates HTTPS URL, non-root DB credentials, SMTP configuration and private storage outside document root. Missing configuration produces a generic unavailable response. Exceptions/SQL/credentials are not returned or logged by the bootstrap. |
| Secrets removed | Previous config, registration/reset/approval/support mail code, weather frontend, driver provisioning and SQL fixture credentials | No embedded JWT key, SMTP password/account configuration, weather credential, shared driver password or usable fixture password remains in application source. Provider webhook URL/token is server configuration. Existing Git history is still potentially exposed and requires rotation. |
| Passwords and role escalation | `includes/security/auth.php`, `general/login.php`, `general/register.php` | `password_hash`/`password_verify` only; public roles limited to customer/owner; every role requires current active account. No plaintext/SHA-256 comparison or submitted-password-to-stored-hash equality fallback. Known exposed and legacy-format credentials require recovery. |
| API tokens | `api/v1/index.php`, `includes/security/auth.php`, Composer `firebase/php-jwt` | Short-lived strictly validated JWTs, opaque refresh tokens stored as hashes, atomic rotation, fixed family expiry and durable family revocation on replay. Sessions capture account version and role so old sessions cannot acquire a changed role through refresh. |
| Web sessions/CSRF | Central bootstrap and existing page/form/AJAX adapters | Strict sessions, private file storage, dedicated HttpOnly/SameSite cookies, production Secure/Host prefix, ID rotation, idle/absolute expiry, current-account revalidation, and CSRF on all web mutations. Login forms/role redirects remain. Logout/read/availability mutations now use POST. |
| Authorization | Global role gates, shared object policies, legacy API adapter, owner/driver/customer controllers | Customer resources remain self-scoped; owners are station/service scoped; drivers are assignment scoped. An assignment-code session cannot read another job, even for the same driver. Insecure alternate review replies now require owner/ownership/CSRF. API DTOs omit task credentials and internal private metadata. |
| Verification/recovery | Hashed challenges and verified reset grants, existing recovery modal and email verification adapter | Expiring single-use OTPs/grants; five-attempt OTP budget; no reset from a request-only session. Reset, restriction and email identity change revoke sessions and outstanding security grants, including pending email changes. New email is not trusted until verified. |
| Driver access | Owner provisioning/incoming-orders, shared driver service and existing driver pages | Random unknowable initial password hashes; one-time, 15-minute hashed job codes; owner-only code issue/reissue; no credential in notifications. Deactivation revokes access while preserving history. State transitions reject other assignments, skipping/terminal revival and duplicate completion. |
| Throttling/CORS | `includes/security/http.php`, API front controllers | Persisted atomic IP/account/user limits, obscured limiter keys, OTP attempt budgets, explicit methods/error statuses, exact-origin CORS without cookie credentials or origin-as-authentication. Untrusted forwarded client-IP values do not bypass limiting. |
| Files | `includes/security/uploads.php`, `includes/media.php`, profile/station/owner registration adapters and server rules | Actual MIME/extension/size/dimension checks, executable/polyglot rejection, generated filenames and private non-executable storage. Owner/admin authorization on verification documents; public station/profile image behavior preserved. |
| Mail and other integrations | `includes/security/mail.php`, `scripts/security-mail-worker.php`, weather/chat proxies | Shared environment-backed SMTP, encrypted mail queue, generic failure logs, bounded retries, configured trusted verification links. Secrets no longer go into frontend weather/chat calls; server-side adapters isolate chat identity. |
| Database permissions | Explicit compatibility/auth migration runner, read-only `clevoEnsure*` wrappers | Former request-time CREATE/ALTER/schema repair/deleting duplicate reviews was removed. Existing helpers now validate deployed schema using SELECT. Migration adds required legacy fields/tables safely, preserving enum members and requiring manual review of duplicate reviews instead of deleting data. HTTP tests use a DB account with SELECT/INSERT/UPDATE/DELETE only. |
| Output and validation | Touched PHP/JavaScript handlers | Parameterized auth/ownership queries, bounded inputs, matching credential policies, safe HTML/JS serialization, text-node insertion for driver/customer/plan data and internal-only upload redirects. |
| Payment authorization containment | `user/station-details.php`, `includes/payment-gateway.php` | New bookings ignore forged client payment markers. Mock card confirmation cannot create production funds/subscriptions (503 until real gateway integration). This does not implement or certify the remaining financial workflows. |

Canonical roles are `admin`, `owner`, `customer`, `driver`; existing `Admin`, `User` and `user` aliases are normalized. No role was removed. Existing Arabic/English content, dark/light controls, PHP page layouts and business entry points were retained; security-related forms/code-display behavior changed where necessary. New verification/recovery text describes the actual state rather than simulated success.

## Configuration and installation

1. **Prepare a protected backup and restored staging database.** Do not import the legacy fixture/bootstrap dump over an existing deployment. The subsequent [database phase](DATABASE_CHANGES.md) separates that snapshot into schema-only initialization and development seeds; follow its versioned upgrade and [recovery runbook](DATABASE_BACKUP_RESTORE.md). Review the actual schema and duplicate reviews before migrating. No live CLEVO database was modified in this phase.
2. Install from `composer.lock` using a supported, patched PHP release with mysqli/mysqlnd, mbstring, fileinfo, OpenSSL and cURL. `composer install --no-dev --prefer-dist --no-interaction` is appropriate for a reviewed deployment artifact. The local test runtime was PHP 8.2.12; it is not an endorsed production patch level.
3. Copy `.env.example` into a **protected configuration file** or inject settings through the hosting secret store. Local `.env` is ignored by Git and denied by supplied server rules. Production should set `CLEVO_ENV_FILE` to a protected file outside public storage, or use process environment variables. Process environment takes precedence. Never paste secrets into documentation, commits, shell history, support chat or logs.
4. Generate **independent cryptographically random** APP_KEY and JWT_SECRET values with at least 32 bytes each. `base64:` followed by base64-encoded random bytes is supported; raw high-entropy values of sufficient length are also supported. Generate/store them directly in the secret manager or protected file, not as terminal output. Example placeholders and missing/equal keys are rejected.
5. Set `APP_ENV=production`, trusted HTTPS `APP_URL` including any application path, and DB host/port/database/username/password. Production refuses a root DB identity or empty DB password. Use a migration identity with DDL rights for migration only and a runtime identity limited to SELECT/INSERT/UPDATE/DELETE on the CLEVO database.
6. Create `PRIVATE_STORAGE_PATH` **outside every web document root and Alias**, owned by the application identity with restrictive OS permissions/ACLs. The application creates private `sessions`, `profiles`, `stations`, `verification` subdirectories. Configure a writable private upload temporary directory in the actual PHP/SAPI configuration; `upload_tmp_dir` cannot be reliably fixed by runtime `ini_set`. Review `deploy/php-security.ini.example`.
7. Configure SMTP host/port/account/password and sender. Production requires SMTP; `MAIL_TRANSPORT=null` is for development/testing only and intentionally discards delivery. Optional weather/chat configuration is server-side; absent values disable the relevant integration with a controlled response rather than exposing a fallback key.
8. Configure exact `CORS_ALLOWED_ORIGINS` for browser API clients; use scheme/host/port only, not the APP_URL path. Leave it empty when no cross-origin browser client is needed. Configure `TRUSTED_PROXIES` only for proxy IPs whose forwarded HTTPS header is controlled. The application deliberately uses the direct peer for IP budgets; a shared reverse proxy requires deployment-specific edge limiting/capacity review.
9. Apply the migration and configure the mail worker before reopening traffic, then validate browser/session/upload behavior and the security suite against the intended deployment stack.

Production serves a generic 503 if required environment or migration state is unavailable. There is no root/blank-password, built-in key, unthrottled-auth or insecure JWT fallback. Setting `APP_ENV=development` on a public deployment bypasses production configuration checks and is not an acceptable production setup.

## Migrations and rollout order

Run the CLI-only `php scripts/migrate-security.php` using the protected migration configuration. For example, set `CLEVO_ENV_FILE` in the process environment to the migration credential file, then invoke the command; never pass credentials as command-line arguments.

The runner takes a database migration lock, verifies a checksum covering the migration SQL/compatibility logic/fingerprint policy, records step progress and applies:

- `migrations/000_base_compatibility.php`: additive equivalents of former runtime repairs for missing legacy booking/notification/service/plan/location/support columns and supplemental tables. It preserves existing status enum members, fills empty bilingual fallbacks once and adds the unique review index only if there are no conflicting review records. It never silently deletes duplicate reviews.
- `migrations/001_auth_security.sql`: auth version, verification/recovery metadata, staged email field, hashed driver-code metadata; persisted auth sessions with role snapshots; hashed refresh records; hashed challenges; rate counters; per-recipient notification reads; encrypted mail queue.
- `migrations/exposed-password-fingerprints.php`: one-way fingerprints of previously exposed fixture hashes. These are not usable password hashes or passwords. The runner identifies those records and unknown legacy password formats, replaces them with random unknowable hashes, marks recovery required and advances auth version without printing values.

Old plaintext OTP/verification/task codes are invalidated. Existing active accounts retain their verified status, while pending owners/customers must use fresh verification links. Modern non-exposed password hashes remain usable. Known demo/shared/legacy credentials require recovery; drivers without recovery email need secure reprovisioning or the owning station's fresh assignment code. Administrators without a valid recovery address require a protected administrative provisioning procedure; do not restore a public default password.

Deploy code, configuration and migrations during a controlled maintenance window. Security bootstrap refuses requests until the complete migration version exists. Existing sessions and old shared-key JWTs are intentionally invalidated; users sign in again. Restart PHP workers when process environment changes. The CLI reports only generic migration failure class/code and counts, never credentials or SQL values.

MySQL/MariaDB DDL is not generally transactional. Step tracking supports safe ordinary reruns, but a crash between a DDL statement and its step record can require inspection/manual reconciliation. A failed migration must be reviewed before retry. Checksums deliberately reject editing an already-started/applied migration; add a new migration for subsequent deployed schema changes. Do not drop tables/columns or restore known vulnerable code as an automatic rollback. Use a tested protected backup/forward-fix plan.

Old verification uploads are not automatically moved or deleted. Authorized legacy delivery resolves existing filenames only under the legacy verification directory. Direct HTTP access to that directory must be denied. Inspect historical stored paths/permissions and copy/relink any files outside that supported legacy location in a separately verified migration; never delete working user documents blindly.

## Required credential rotation

The repository previously contained usable credential material. Removal from the working tree does not invalidate it, cached frontend copies, clones, backups or Git history. **External rotations have not been performed** because this phase changes application code and documents the operational process.

| Potential exposure | Where it previously appeared | Required operator action |
|---|---|---|
| JWT HMAC signing key | `includes/config.php`, historical commits/clones | Create a new independent high-entropy signing key, revoke all existing sessions/refresh families in a controlled transaction, update protected configuration and restart workers. Never reuse the old source value. Old JWTs are also rejected by the new claim/session requirements. |
| SMTP mailbox/application password | Registration, reset mail, station approval and support helpers | Revoke exposed provider application passwords, issue a least-privilege sending credential, update SMTP configuration, restart workers, review provider sign-in/sending activity and test authorized staging delivery. Protect the mailbox's own login/recovery controls. |
| Weather API key | Customer-home JavaScript and browser/CDN caches | Revoke/rotate at the provider, restrict usage/IPs/quotas where supported, update the server-side configuration and invalidate cached frontend artifacts. Verify no key is returned by the proxy. |
| Chat webhook endpoint / any provider token | Browser chatbot JavaScript, browser requests/history | Treat the exposed endpoint as public; rotate its secret URL/token if it provided implicit authentication, configure authenticated server access/rate limits, review provider logs and session isolation. Do not consider moving the same URL to .env a rotation. |
| Administrator/demo/shared driver credentials | SQL fixtures, driver provisioning and historical account rows | Run the migration, review privileged accounts and activity, perform verified recovery/reprovisioning, issue fresh driver codes and revoke affected sessions. Do not reactivate a known default credential to simplify testing. |
| Database identity | Local source configuration previously used privileged access | Provision separate least-privilege runtime and migration identities; change any reused database credential, disable remote/root access for the app, review grants and protect backups. Do not copy local blank-password conventions into production. |
| APP_KEY (new secret) | Protected environment only | Protect separately from JWT signing. Rotation invalidates challenge/limiter HMACs and encrypted queued mail: drain or invalidate/resend pending messages/challenges under maintenance, replace the key and restart workers. Preserve needed key material only in protected rotation/backup systems. |

General sequence: restrict exposure -> issue replacement at the provider/secret store -> deploy new protected configuration -> revoke old credential and affected sessions -> restart/cache-purge as relevant -> verify with synthetic accounts -> review provider/audit activity -> remove exposed historical artifacts through a separately reviewed history/backup cleanup. Provider overlap/rollback rules must not leave the exposed credential valid indefinitely. No Git history rewrite or remote action was performed here.

When recording rotation completion, capture provider credential identifiers, timestamps, operator, revoked/active state and verification outcome; record **no secret value**, OTP, grant, JWT or refresh token.

## Mail worker and safe logging

Schedule `php scripts/security-mail-worker.php` at least every minute or supervise it as a CLI task using the protected runtime environment. It processes bounded batches, locks pending records, retries failures up to five times, and clears encrypted payload after success. SMTP success cannot be atomic with a database commit: a crash can duplicate an email; its token is still single-use. Monitor unsent/exhausted records and arrange retry/resend before authentication-link expiry.

Mail recipients/content, including OTPs and verification links, are AES-256-GCM encrypted at rest with authenticated context. The worker logs queue record IDs and generic failures only. It does not log PHPMailer exception messages, SMTP debugging or credentials. The same worker prunes expired limiter/challenge/session records; used refresh records are retained through family lifetime for replay detection.

Use the supplied `.htaccess` files and equivalent real web-server rules to deny configuration/VCS/dependency/test/migration/worker/private-document access, directory listing and uploaded executable types. `deploy/apache-security.conf.example` demonstrates path-only access logging; do not log query strings, Authorization/Cookie headers or bodies at proxies/APM/debug middleware either. Verify the **effective** Apache/proxy configuration; the test router is not proof that hosting obeys these rules.

## Known limits and remaining work

- Production deployment, provider credential changes, real SMTP/bounces/domain authentication, actual Apache TLS/AllowOverride/proxy behavior, production MySQL version and backup restoration were not executed. The test environment uses isolated MariaDB with a restricted runtime account and a null mail transport.
- Existing financial settlement/refund/concurrency/plan economics issues outside authentication remain in the audit. Real card processing is not implemented; mock production confirmation is blocked. This project is not commercially ready solely because these security tests pass.
- Existing dashboards were exercised through HTTP and their generated JavaScript compiled; full browser interaction, visual AR/EN/theme regression, hardware/mobile secure storage, background tracking and app-link configuration remain unverified. No Flutter app was created in this phase.
- Upload inspection and private storage do not replace a malware scanner or historical-upload review. Public images are intentionally public; verification documents require authorization. Native bearer document download is a future API slice.
- The file-session implementation is suitable for the existing single/shared-filesystem deployment. Multi-host sessions, distributed edge limiting, MFA/step-up for administrators/payouts and broader monitoring need separate deployment/product work.
- Required OS permissions, private temporary directories, secret injection, runtime patching, mail scheduling and server denies are operational gates. Code cannot establish those properties on an unconfigured host.

This phase stops after the authentication/security implementation, migrations, configuration examples, API documentation and executed tests. It does not claim that application security is complete.
