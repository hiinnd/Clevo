# CLEVO Android release checklist

Reviewed 2026-11-22 against official requirements. One Flutter application provides customer, owner and driver experiences. `com.clevo.clevo` is the existing identifier; ownership/store availability are **unconfirmed**. PHP Admin stays on the web. No Play submission or production signing key was created.

- [ ] Approve legal operator, support/privacy contacts, package ID and store account ownership. Reserve the final identity before registering Firebase/Maps/payment redirects; changes after publication are a new app identity.
- [ ] Use a reviewed staging public config with actual HTTPS API, separate staging Firebase/native config and restricted Maps key. Example JSON contains no secrets and intentionally uses `.invalid`. Never put JWT, SMTP, payment server keys, service-account JSON or signing passwords in dart-defines/assets.
- [ ] Generate the real upload/signing material only through an approved private key-management process; store outside Git and the repository, back it up separately, restrict access and record recovery custody. Configure ignored `android/key.properties`, use Play App Signing and protect upload-key recovery. Gradle rejects missing credentials, in-repo keystores and known debug signing. Check the actual certificate fingerprint; the check is not a key-strength certification.
- [ ] Run `scripts/mobile-release-preflight.php <public-config.json>`, Flutter analyze/tests, backend staging tests, dependency audits and `composer check-platform-reqs` for the API. Review all false checks before approval. `scripts/build-internal-android.ps1` prepares a locally signed internal APK only after configuration gates pass, never uploads it. Its `.internal` identifier needs a matching staging Firebase registration/signing restriction; adapt the provisional identifier to approved ownership before use.
- [ ] Build the final production app bundle using `flutter build appbundle --release --dart-define-from-file=<public-config.json>` in the approved build environment, with final ID/label, monotonically increasing build number and reviewed version. The release runtime rejects placeholder/local/insecure API URLs. Keep symbols/mapping files and artifact hashes privately; inspect the exact final bundle, not an old debug APK.
- [ ] Verify target API **36+** for new apps/updates, current SDK/plugin compatibility and native page-size compliance for every ABI. API36 has applied since 2026-08-31; do not assume a prior extension still applies. [Play target policy](https://support.google.com/googleplay/android-developer/answer/11926878).
- [ ] Run `zipalign -c -P 16 -v 4 <apk>` and inspect each packaged ELF LOAD alignment (minimum 0x4000), then test a 16 KiB Android runtime and the Play bundle-generated APKs. NDK version alone is not evidence. [Android page-size guide](https://developer.android.com/guide/practices/page-sizes).
- [ ] Inspect merged release manifest: no debuggable/cleartext/debug network-security overrides, backups disabled as intended, exported components scoped, notification prompt on supported Android, foreground location only during assigned active jobs. No background location/service permission has been approved. Camera/microphone/background permissions must not be added speculatively.
- [ ] Test secure storage, token refresh/revoke, role/IDOR boundaries, pickup GPS permission denial/staleness, process kill/resume, real network loss, Maps/FCM/deep links and verified sandbox checkout return. Granting a permission is not a reason to track outside active jobs.
- [ ] Publish approved active public HTML privacy/terms/support and web deletion URLs; prove in-app and out-of-app deletion actually complete after review, including processor cleanup and disclosed retention. Draft 503 pages are not submission URLs. Complete Play Data safety from actual backend/SDK data flows; no fabricated no-data declaration. [Deletion policy](https://support.google.com/googleplay/android-developer/answer/13327111).
- [ ] Prepare screenshots in Arabic/English, content/age declarations, service description, support contacts and reviewer test accounts for all three roles. Use real sandbox functionality, no hidden fake production success or real customer credentials.
- [ ] After explicit publishing approval, upload to internal testing, inspect pre-launch report and invite approved testers. For applicable personal accounts created after 2023-11-13, production access also requires at least 12 opted-in closed testers continuously for 14 days; internal testing does not satisfy that gate. [Play testing requirements](https://support.google.com/googleplay/android-developer/answer/14151465).
- [ ] Obtain release sign-off after target-device/security/accessibility/performance tests and final production health/backup/provider approvals. No device, internal Play distribution or signed production AAB has been verified locally.
