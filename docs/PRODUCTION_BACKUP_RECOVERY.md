# CLEVO backup and recovery plan

Prepared 2026-11-22. No production backup repository exists or is approved. Automated services are templates and have not been installed. Local restoration evidence belongs in [PRODUCTION_TEST_RESULTS.md](PRODUCTION_TEST_RESULTS.md), independently of the production gates below.

## Proposed policy and implementation

Proposed minimum RPO: 24 hours; proposed RTO: 4 hours. Neither is an approved/measured production commitment. Obtain business approval; online payments may require a shorter RPO, managed binlog archiving/PITR and continuous reconciliation. The supplied daily logical snapshot is not PITR or high availability.

`scripts/backup-database.php` uses an InnoDB consistent snapshot, UTC, native matching dump client, hex blobs, routines/events/triggers, no tablespaces and no database creation/drop-table statements. Abort if non-InnoDB tables prevent a consistent snapshot. A protected manifest records time, bytes and SHA-256. The password is supplied via a temporary 0600 client option file, removed on both success and failure; never on the command line. Failed/partial dumps have no valid manifest and must not be restored. Run under the dedicated backup identity, not a runtime or administrator password.

Use matching MySQL/MariaDB clients. `DB_CLIENT_FLAVOR=mysql` uses VERIFY_IDENTITY; MariaDB uses its server certificate verification switch. Remote DB CA verification is mandatory; do not use insecure skip switches. On MySQL with GTIDs, use reviewed client settings and rehearse without granting unnecessary global privileges. Do not back up mysql system users/password tables as application data. Consult the [MySQL dump privilege/options reference](https://dev.mysql.com/doc/refman/8.4/en/mysqldump.html) before finalizing grants on the approved server.

`deploy/bin/backup.sh` wraps the logical dump and explicitly selected private profile/verification files in an encrypted restic backup, checks the repository and writes a last-success health marker **only after both commands succeed**. It excludes env/secrets, sessions, client files, OTP queues as separate files and upload temp directories. The SQL itself necessarily contains protected application data, including encrypted fields. Store essential decryption/signing secrets separately in an independently recoverable secret manager; do not place them in the same backup bucket/repo password file. Private media and SQL are not globally atomic; deletion/attachment references must be reconciled on restore, and a maintenance snapshot is preferable for disaster recovery evidence.

Provision the encrypted repo only after approval, using a restricted bucket/account, a separate random repository password, TLS verification, encryption, versioning/immutability appropriate to the retention policy, and an off-host failure domain. `clevo-backup.service.example` / timer are unactivated. The reference unit uses the trusted application OS identity because current uploads/heartbeats are 0600, but supplies a separate SELECT-only DB profile; it is not an independently isolated OS backup agent. Its service filesystem sandbox permits writing only backup/ops/cache paths. Qualify a provider-managed or separately isolated backup agent before claiming stronger host-compromise separation. Never embed bucket credentials in a unit, Git, process arguments or shell history. Protect the local plaintext staging dump on encrypted volumes; monitor free space. Automatic deletion, `restic forget/prune` and SQL dump cleanup are deliberately absent pending approved retention periods. This means disk-space alerts and an operator retention procedure are mandatory before activation.

Proposed scheduling: daily full snapshot, daily repository metadata check, weekly authenticated full-data repository check, monthly disposable DB/file restore, before every migration and after any client/server/permission change. A proposal of 7 daily/4 weekly/12 monthly recovery points needs financial/privacy approval before implementation; do not interpret it as a legal retention rule. Alert if last-success exceeds 90,000 seconds or service/repository integrity fails.

## Restore rehearsal

1. Use synthetic data or an authorized, access-controlled recovery environment. Verify the selected encrypted snapshot and its date/source. Restore into a fresh private directory with no web access; never overwrite production. Validate the dump SHA-256 and media hashes. Test missing/corrupt manifest rejection.
2. Create an empty disposable target on loopback with the required `clevo_restore_test_<12 lowercase hex>` name, APP_ENV=testing and a separate restore environment. `scripts/restore-disposable.php <private/backups/file.sql>` refuses any other target, nonempty schema, mismatched checksum, unprotected path or database-switching commands. It is a rehearsal tool, **not** a production restore script.
3. Compare every table's row counts, FK integrity, schema versions/checksums, integer-fils journal debits/credits and owner/platform totals; verify all media references and private authorization. The existing `tests/database.php` performs disposable native dump/restore and financial/count comparisons. Validate the same on the approved MySQL target before launch.
4. Before routing traffic to any recovered copy: replay the restricted erasure register/tombstones generated after its snapshot, remove restored personal media/locations and revoke old sessions/device tokens where required. Preserve financial/legal evidence under the reviewed policy. Restoring old personal data must not undo approved account deletion.
5. Reconcile outbox/mail/webhook leases and provider states before restarting workers. A snapshot can contain queued messages already delivered externally after its timestamp. Do not blindly resend mail or reissue charges/refunds. Refresh provider status via approved read-only reconciliation, document unknown results and resolve them without synthetic success.
6. Record operator, snapshot ID/hash, start/end, measured RTO, counts/balances, media hashes, exceptions, privacy replay and the final independent approval. Test loss of the primary host and restore credentials, not just a file on its own disk.

Only after this evidence and explicit approval may operators plan a production cutover. No DROP, real-data reset or destructive production restore was performed in this phase.
