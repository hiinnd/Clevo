# CLEVO project audit

Audit date: 2026-11-15 (Asia/Amman). Repository baseline: `e85903e` (`reset`). Scope: audit and documentation only. No application, database, dependency, or deployment changes were made.

## Decision

**Do not launch the current implementation commercially.** Account recovery, public role assignment, payment confirmation, booking payment fields, signing-key management, and uploads have release-blocking defects. The PHP/MySQL application has substantial reusable functionality; an incremental API extraction is appropriate. A backend replacement is unnecessary.

The target design is in [TARGET_ARCHITECTURE.md](TARGET_ARCHITECTURE.md), execution dependencies in [MIGRATION_PLAN.md](MIGRATION_PLAN.md), and file/endpoint coverage in [FEATURE_INVENTORY.md](FEATURE_INVENTORY.md). Proposed remediation in these documents has **not** been implemented.

## Evidence and limits

- Reviewed the first-party PHP controllers, helpers and embedded templates/scripts across `admin`, `api`, `driver`, `Emails`, `general`, `includes`, `owner`, `scripts`, and `user`; all three JavaScript assets; the SQL schema and seed relationships; Composer manifests, installed package metadata, `.gitignore`, and editor configuration. Inventory: **67 PHP files, 3 JavaScript files, 17 SQL tables**. PHP sources contain approximately 24,000 lines including markup and blank lines.
- Inspected the vendored dependency's identity and Composer audit results, rather than treating upstream vendor code as first-party implementation. Image/upload assets were inventoried; no claim is made that binary uploads were malware-scanned or that every image was visually inspected.
- `php -l` passed for **67/67** first-party PHP files using local PHP **8.2.12**. `node --check` passed for **3/3** standalone JavaScript assets. Embedded PHP-generated JavaScript was reviewed statically, not executed in a browser.
- `composer validate --no-check-publish --no-interaction` passed with a missing-license warning. `composer audit --locked --no-interaction --format=json` returned empty advisory and abandoned-package lists. A nonfatal Composer cache-write warning occurred. This is a point-in-time advisory check, not proof of application security.
- A read-only database connection attempt, without including the application bootstrap, failed with MySQL client error **2002**. No SQL dump was imported, server started, live data queried, or business request submitted. The installed client identifies as **MariaDB 10.4.32**; this does **not** establish the running database engine/version.
- An in-memory test of extracted JWT functions with an ephemeral key verified normal round-trip, rejection of a changed signature and expired token, and acceptance of a correctly signed token containing an unexpected header algorithm, wrong issuer, and future `iat`. No real tokens or keys were printed.
- A static parser checked seed relationships. It found six driver/station ownership mismatches. The checked foreign-key relationships had no dangling seed IDs; booking/service station matches, wallet nonnegative balances, wallet-user uniqueness, and order-number uniqueness passed **for the supplied seeds only**. No database constraint enforcement or import compatibility was exercised.
- No authenticated browser, mobile, payment-provider, SMTP, FCM, load, concurrency, restore, or penetration test was performed. No provider was contacted to send mail, charge money, or deliver notifications.

**Status vocabulary:** `CONFIRMED` means established from source/data or the stated isolated check. It does not mean exploited against a running service. `SUSPECTED` means a plausible consequence requiring runtime or policy evidence. `UNTESTED` means a required capability/environment has not been verified. Severity applies independently: **CRITICAL** = account/platform compromise or unauthorized financial issuance; **HIGH** = major authorization, financial integrity, data-loss or launch blocker; **MEDIUM** = bounded correctness, validation, operability or scaling defect; **LOW** = minor UX, maintenance or dormant feature gap. Line references refer to this baseline and are 1-based.

## Confirmed findings

### Authentication, authorization and secrets

| ID | Severity | Status | Evidence and impact | Required remediation / acceptance evidence |
|---|---|---|---|---|
| A01 | CRITICAL | CONFIRMED | `general/send-reset-otp.php:62-85` sets `reset_user_id` before OTP verification. `general/login.php:199-244` accepts that session value plus CSRF and a nonempty password, without checking that OTP verification succeeded. `general/verify-reset-otp.php:38-55` returns success but creates no verified reset grant. The supplied schema has foreign keys for stations/services/bookings/reviews/wallets/subscriptions/support; it is not relationship-free. It also creates a nullable circular user-to-station/owner-to-user relationship (`clevo.sql:43,97,362-363`), which needs deliberate creation/archive ordering.

## Required test coverage

No application test suite currently establishes these behaviors. The following are release gates, not tests claimed to have passed:

1. **Authentication/authorization:** all four roles; public privilege injection; account/owner approval; session fixation and cookie settings; banned/removed users; JWT invalid signatures/claims/revocation; reset bypass, expiry, retry/replay and enumeration; email changes and verification.
2. **Booking matrix:** station/home/delivery; individual/multiple services; station approval/availability; slot boundaries and concurrency; owner accept/reject/assign; driver ownership and stale sessions; every legal/illegal transition; reschedule/deadline behavior; terminal states.
3. **Financial invariants:** wallet/points/plan/cash/card; mixed points discounts; exact rounding; duplicate/replayed mobile commands and payment events; webhook signature/amount/currency/reference mismatches; partial failure at each step; concurrent debit/refund/completion/withdrawal; negative balances; owner reserves; ledger reconciliation.
4. **Subscriptions/loyalty:** term snapshots, last wash race, eligibility, expiration, consume/restore exactly once, plan edits/deactivation and fixture imports; no repeated loyalty credit or concurrent over-redemption.
5. **Data safety:** archive service/station/user without losing booking/financial history; relationship cleanup reports; migration on realistic anonymized data; full backup and restore; engine/strict-mode compatibility.
6. **Features/integrations:** support for every role and guests; retained conversation history; two-admin notification reads; AR/EN and dark/light; upload/download authorization; map stale/offline/permission handling; mail retry; push token rotation; chatbot isolation. Provider sandbox/device tests remain necessary.
7. **API/mobile/operations:** OpenAPI conformance, deterministic 4xx/5xx errors, pagination, rate limiting, correlation IDs without secrets, bounded payloads, HTTPS/deep links, offline retry/idempotency, physical Android/iOS background tracking, representative load, worker crash/retry and restore drill.

## Components worth preserving

Prepared statements and object scoping are already used in many controllers; CSRF helpers and escaped output exist; login regenerates session IDs; wallet debit uses an atomic sufficient-balance condition; some cancellation/reschedule/withdrawal flows use transactions and row locks; booking-service snapshots and bilingual database columns exist. These are useful starting points, **not blanket guarantees**. Reuse the domain concepts and hardened code through shared services, while fixing unsafe alternate paths and retaining existing web roles/UI.

## Completion boundary

Audit and design documentation are complete for the available repository. Production readiness, live schema correctness and integration behavior remain unverified until the documented runtime gates are executed. Stop here: implementation and deployment are outside this phase.
